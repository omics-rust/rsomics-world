## Machine, fixture, and method

The host was `dell-Precision-7920-Tower`, Ubuntu 22.04, Linux 6.8,
`x86_64`, with two Intel Xeon Gold 6238R CPUs. All project source, binaries,
fixtures, temporary files, and results stayed under
`/data1/liangjy/rsomics-linux-x86_64-20260730`.

The full input was `SRR341550_1.fastq.gz`, SHA-256
`d7a15c1762d64a5434ced0cc665d7f5d167ca81a71e239f8237b9cd490dd7683`,
with 6,282,141 reads. The 100,000-read k-mer subset had SHA-256
`2b5e03ad577059d432c1ce986bf1a850bc6402b4f17ef7f41015278e4bfb18a3`.

Commands were bound to physical cores 48–51 on one socket. Hyperfine used one
warmup and ten measured runs, except the five-run k-mer comparison. Timed
record output went to `/dev/null`; correctness outputs were materialized and
compared separately. Peak RSS is from separate GNU `time -v` runs. Other users
had jobs on the host, so the core binding and observed distributions are part
of the provenance.

## Thread-control finding and resolution

The measured product head accepted common's former shared `--threads` flag but
did not use the configured Rayon pool. Compressed input uses one decompression
worker feeding the streaming consumer.

Five-run controls measured:

- stats at one versus four requested threads:
  `1.118 ± 0.021 s` versus `1.110 ± 0.007 s`;
- sequence grep at one versus four requested threads:
  `5.945 ± 0.037 s` versus `6.279 ± 0.363 s`.

No scaling is demonstrated. The performance table therefore describes a
four-core affinity allocation, not a four-thread product mode. Alignment head
`2727daa3bf4f` removes the flag and the unrelated seed/verbosity controls while
retaining preprocessing's separate real thread control.

## Remaining limitation

representative performance host. The performance claims remain limited to the
recorded Linux `x86_64` machine. `rsomics-kmer 0.2.1` is a corrective release
for the existing public foundation; further API growth still requires a
second current target-product consumer.
