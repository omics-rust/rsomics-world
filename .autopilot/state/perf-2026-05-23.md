## bamio 0.1.7 zero-copy read API — checksum -t1 before/after diagnosis — 2026-05-23

Added `rsomics_bamio::raw::RecordReader` / `RecordRef`: a borrowing,
allocation-free record scan that reads each record straight out of the BGZF
reader's already-inflated block buffer (only a block-straddling record spills
into a reused scratch buffer). Rewrote `rsomics-bam-checksum` onto it. Same
machine (Apple M2, 8 cores, macOS arm64), fixture `bench_3M.bam` (170 MB,
3,000,000 records, sha256 65d254b0…), samtools 1.23.1.

Controlled 3-way hyperfine, warmup 3, 20 min-runs, ours -t1 vs samtools
single-thread (`-@ 0`). before = HEAD checksum (owned `read_record`), after =
`RecordReader` rewrite; before/after stdout byte-identical, and both match
samtools' checksum line by line.

| variant | mean (ms) | σ | user (ms) | ratio vs samtools |
|---|---|---|---|---|
| before (-t1, read_record) | 977.4 | 11.4 | 953.2 | 0.99× |
| after  (-t1, RecordReader) | 989.6 | 10.8 | 965.4 | 0.97× |
| samtools (single-thread) | 964.4 | 15.2 | 927.3 | 1.00× |

**Verdict: NOT a CPU win. before ≈ after within σ (977±11 vs 990±11) — the
zero-copy read does not move checksum's wall-clock.**

Diagnosis (Instruments `sample`, profiling build, resolved symbols, 511 MB
3×fixture so the run outlives the sampler):

- `libdeflate_deflate_decompress_ex` — 816 self samples (BGZF inflate). samtools
  uses the *same* libdeflate, so this is a wash by construction.
- `run_checksum` (inlined `fill_seq_qual` + loop) — 363.
- `crc32fast::Hasher::update` — 203 (+ `crc32_arm_pmullx12` 17). CRC over every
  base + every qual byte, per record.
- `_platform_memmove` — **22** (~1%). The per-record copy the task targeted is
  ~1% of CPU, not the bottleneck.

The original premise ("0.96× lost entirely to alloc+copy") does not hold under
the profile: checksum is inflate-bound + CRC-bound, and `read_record` already
reused one `RawRecord` buffer across records, so the only avoidable cost was the
`read_exact` copy (~1%). Removing it lands inside the noise floor. A pure
read+hash tool that CRCs every byte cannot beat its C reference by killing a 1%
copy when 95% of the CPU is shared libdeflate inflate + hardware CRC.

**Real win — memory axis:** peak RSS ours 2.74 MB vs samtools 6.62 MB (2.4×
less). The borrowing reader holds one BGZF block, never a growing record buffer.

The `RecordReader` API is correct (byte-exact across single/multi-worker and a
multi-block straddle test) and is the right primitive for genuinely read-light
scans that do *not* also hash every byte. It is not, by itself, enough to push
the hash-bound checksum past 1.0×; closing that 3% would require swapping
`crc32fast` for libdeflate's `libdeflate_crc32` (what samtools calls) — a
checksum-crate change outside this task's bamio scope, logged here as the next
lever.

## MultithreadedReader bounded(1) — already fixed upstream (noodles-bgzf 0.47)

Problem 2 (the `bounded(1)` block-lookahead cap) does not exist in the pinned
noodles-bgzf 0.47.0: `MultithreadedReader::with_worker_count` allocates
`crossbeam_channel::bounded(worker_count)` for the inflate / read / recycle
channels (multithreaded_reader.rs:185-187). The lone `bounded(1)` is the
inner per-block ordered hand-off (`buffered_tx`), which is by design (it
preserves block order), not a lookahead cap. No change made to the MT reader —
the lookahead is already `= worker_count`, so widening it here would diverge
from upstream with no measured benefit. calmd -t4 was not re-benched because the
MT reader was not touched.
